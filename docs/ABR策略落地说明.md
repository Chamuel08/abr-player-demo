# iOS ABR 播放器：策略落地与离线验证

## 一、背景

这个 demo 要验证的是一件事：**把一个音视频策略从机理设计做到可量化验证的落地，需要哪些环节，以及每个环节靠什么判断对错。**

选 ABR（码率自适应）作为题目，因为它是策略密度最高的一块：决策直接影响卡顿、画质、切档三个互相冲突的指标，而参数取值的合理性无法靠肉眼观察播放画面来判断 —— 必须靠数据。

目标不是做可上线的播放器，而是把**"策略参数凭什么取这个值"**完整走通一遍。

- 实现：Swift 5.9 / SwiftUI / AVFoundation，iOS 16+，无第三方依赖
- 离线校准：Python 标准库，无第三方依赖
- 数据：166 条公开真实网络吞吐 trace（MERINA MM'22 整理，学界 ABR 通用）

项目是这次面试之后做的。面试时问到 iOS 开发经验，我答的是没有 —— 所以这里的重心放在能迁移的部分：策略机理与验证方法，而不是 iOS 平台本身的熟练度。

## 二、结论

### 2.1 交付范围

自实现 BBA 与 MPC 两种 ABR 策略，支持运行时切换；配套一层离线校准，用真实 trace 做大规模参数搜索。

### 2.2 关键结果

**1. 参数搜索有效，经验取值存在明显改进空间。** BBA 在 FCC+HSDPA 训练集搜参、测试集报数：

| 来源 | 平均码率 | 卡顿 | 切档次数 |
|---|---|---|---|
| 经验默认值 | 562 kbps | 10.33s | 41.8 |
| 搜索最优 | **821 kbps**（+46%） | **10.10s** | **16.4**（减半） |

**2. 离线验证发现并修正了 MPC 的一处实现缺陷。** 初版 MPC 的预测窗口设成 5s ≈ reservoir，导致代价函数里的卡顿项恒为 0 —— MPC 看不见卡顿风险，只顾冲画质。改成按 segment 决策后：

| 配置 | 卡顿 | 平均码率 | 切档次数 | QoE |
|---|---|---|---|---|
| BBA 基线 | 10.33s | 562 kbps | 41.8 | −0.826 |
| MPC 初版（窗口 5s） | 10.37s | 2498 kbps | 118.9 | −4.693 |
| MPC 修正后（窗口 20s） | **10.26s** | 501 kbps | **15.0** | **−0.791** |

卡顿低于 BBA、切档减少 64%、QoE 反超，验收通过。

**3. 识别出一个会导致假结论的实验设计陷阱。** 首轮搜参 125 组参数的卡顿数完全相同、Pareto 前沿退化成一个点，表面结论是"参数搜索无效"。真实原因是实验条件没有约束到被测机理 —— 程序完全正常，但结论是错的。

### 2.3 结果解读

三条结果对应三个层次：第 1 条是策略调优的常规产出，第 2 条是**用数据反向检验自己的实现**，第 3 条是**对数据的取得方式本身保持怀疑**。

后两条是我认为更值得说明的部分。策略开发中成本最高的环节不是写出策略，而是判断策略是否有效 —— 前者 AI 可以承担，后者不能。上表中那个 5 秒预测窗口，恰恰是 AI 生成的。

## 三、实施过程

### 3.1 BBA：建立安全基线

只看 buffer 水位决定码率，不依赖带宽预测：

```
buffer < reservoir(5s)                    → 强制最低档
buffer > reservoir + cushion(5+10 = 15s)  → 冲最高档
中间                                       → 线性插值后滞回量化
```

两个设计选择：

**为什么不直接上 MPC。** BBA 不需要准确的带宽预测，对抖动天然鲁棒，是后续所有策略的对照基线 —— 没有基线，MPC 好不好无从判断。

**滞回为什么不对称**（升档保守、降档激进）。画质降级可逆、用户容忍度高；卡顿不可逆、直接掉体验。所以升档要求 `raw ≥ candidate × hysteresis` 才动，降档只要 `raw < candidate / hysteresis` 立刻动。

### 3.2 MPC：滚动时域优化

把选档建模为序列决策：当前选档影响未来 buffer、卡顿、画质。

- **预测模型**：`buffer(t+1) = buffer(t) + dt·(throughput/bitrate − 1)`，吞吐用 EWMA（α=0.3）估计
- **代价函数**：`J = Σ[w_stall·stallSeconds + w_quality·dt·(max−br)/max] + w_switch·switch`
- **求解**：对每个候选档位做"保持该档位"的时域展开，取代价最小者。档位离散且只有 5 个，穷举即可，单次 <1ms

**关键设计：MPC 保留 BBA 兜底。** 三种情况跳过优化、强制最低档：`buffer < reservoir` / 弱网 / 无吞吐观测。

MPC 的全部收益建立在"预测大致准"之上，而预测一定会在某些时刻失效。策略必须有一个**不依赖预测的下界** —— 即使预测完全错，也不会比 BBA 更差。这不是防御性编程，是策略设计本身的一部分。

### 3.3 离线校准层与验证边界

初版参数 `reservoir=5 / cushion=10 / hysteresis=0.8` 是工程经验值。经验值不一定错，但没法回答"换成 6 秒会更好吗"。

项目约束要求"必须用真实 HLS 流验证"，但几千组参数 × 每组数百秒的真机回放不可行。于是分两层，边界写死：

| 层 | 载体 | 数据 | 职责 |
|---|---|---|---|
| 离线仿真 | Python | 公开真实吞吐 trace | 大规模搜参，产出候选与 Pareto 前沿 |
| 真机验收 | iOS + Network Link Conditioner | 真实 HLS 流 | 只验 2~3 组候选，确认结论在真实 AVPlayer 上成立 |

**离线层不替代真机验收，它只负责缩小搜索空间。** 任何参数写回 Swift 之前必须过真机验收 —— 这条纪律写进了 spec，不是口头约定。

仿真结论能不能采信，取决于三条纪律：

1. **决策逻辑与 Swift 逐行对齐。** 两边不一致时以 Swift 为准，改仿真器。
2. **buffer 动力学独立推演，不复用 MPC 的预测模型。** 按"下载进度 + 播放消耗"真实演算。否则 MPC 会在自己的假设里自证 —— 预测说不会卡，仿真就真的不卡，结论漂亮但毫无意义。
3. **首帧与卡顿分开计。** 起播前的 buffer 填充是首帧耗时，不是 rebuffer。混在一起会让所有参数组合的卡顿数趋同，掩盖差异。

搜参用 FCC+HSDPA 自带的 train/test 划分（166 条训练、117 条测试），避免过拟合。

### 3.4 首轮结果的失效诊断

首轮搜参：125 组参数卡顿数完全相同，Pareto 前沿退化成一个点。

看起来是"参数搜索没用"。真实原因是 trace 平均吞吐约 1.4 Mbps，而码率阶梯最低档只有 246 kbps —— **任何选档都不可能引起卡顿**，卡顿全部来自 trace 里吞吐归零的断网，与算法无关。参数根本没有发挥作用的空间。

把 trace 吞吐缩放到 0.3 倍让档位真正约束决策，前沿才出现 4 个点，也才有了第二节那张 BBA 搜参表。

这个陷阱的要害是**误判方向**：搜索程序完全正常，不报错、不崩溃、输出格式也对，但它会让人得出一个错误结论。一个不触发目标机制的实验，会自信地报出"无显著差异"。

同类失效在生产 A/B 测试里同样存在 —— 如果实验流量的网络条件没有覆盖策略真正起作用的区间，测出来的"无效果"是假的。沉淀成一条判据：**看到"无显著差异"，先验证实验条件是否触发了被测机理，再评价策略。**

### 3.5 MPC 时域粒度的定位与修正

**现象。** 验收标准是"MPC 卡顿 ≤ BBA"，仿真显示不满足：MPC 卡顿 10.37s 略高于 BBA 的 10.33s，同时码率虚高到 4.4 倍、切档近 3 倍，QoE −4.693 远差于 BBA。真机上单看播放画面，这个版本"是能跑的"，问题不显眼。

**根因。** 顺着代价函数查下去，是预测粒度选错了。初版按控制周期推进预测：`dt = 0.5s`，`H = 10`，窗口 5s。而 MPC 只在 `buffer ≥ reservoir = 5s` 时才启用 —— rollout 从 5 秒起步往前推 5 秒，即使一路下跌也刚好在时域末尾摸到 0。**卡顿项恒为 0。** J 里只剩画质项和切档项可优化，MPC 于是只管冲最高档。它不是算错了，是压根看不见卡顿风险。

**修正。** 对照 ABR 领域的标准形式（FastMPC/RobustMPC, Yin et al. SIGCOMM '15），MPC 应当按 segment 决策：`dt = segment 时长 = 4s`，`H = 5`，窗口 20s 远超 reservoir，卡顿项才始终是活的。

这个缺陷的来源需要交代清楚：初版的 0.5s 控制周期本身就是对标准形式的偏离 —— 把 segment 粒度下的 `H=10` 直接搬到了 tick 粒度上。熟悉 ABR 的人不会这么选，因此也碰不到这个坑。

所以它的价值不在于"发现了一个隐蔽 bug"，而在于**验证体系把一个自己引入的偏离纠了回来**。缺陷可以靠经验避免，也可以靠验证兜住 —— 我暂时没有前者，所以必须有后者。

配套改两处，否则粒度切换会引入新的失真：

- **卡顿惩罚按秒计，不按步数计。** 原来每步见底记一次卡顿，惩罚量纲会随 `dt` 漂移（dt 减半、同样的卡顿被记两倍次数），调时域参数会意外改变卡顿与画质的相对权重，让搜参结论失效。改成线性插值折算实际见底秒数后，`w_stall` 的含义固定为"每秒卡顿的代价"。
- **决策节奏与安全兜底解耦。** rollout 只在 segment 边界重算，但三条安全兜底仍每 0.5s 检查。否则降档反应慢 4 倍，等于拿卡顿换切档平稳，是笔坏交易。

**验证。** 为确认 20s 不是碰巧取到的好值，固定 `dt=4s` 扫描窗口长度：

| H | 窗口 | 卡顿 | 平均码率 | 切档次数 |
|---|---|---|---|---|
| 1 | 4s | 10.32s | 2490 kbps | 36.7 |
| 2 | 8s | 10.30s | 1853 kbps | 39.0 |
| 3 | 12s | 10.24s | 725 kbps | 19.1 |
| 5 | 20s | 10.26s | 501 kbps | 15.0 |
| 8 | 32s | 10.10s | 483 kbps | 11.1 |

窗口 ≤ 8s 时卡顿项基本失效（码率虚高、切档频繁），跨过 12s 后行为才稳定。沉淀成一条判据写进 spec：**`horizon × dt` 必须显著大于 `reservoir`。**

### 3.6 工程流程与 AI 分工

用 spec → plan → tasks → implement 的顺序推进，规则是 spec 先于 plan、plan 先于 tasks；implement 阶段发现 spec 不可行时回去改 spec，不允许直接绕过。上面 3.5 的修正就是这么走的：先改 spec-mpc.md 加 CRITICAL 约束，再改代码。

AI 负责代码产出，我负责定义验收标准、判断结论是否成立。**AI 加速的是打字，不是判断** —— 3.5 那个 5 秒预测窗口就是 AI 写出来的，把它揪出来的是验收标准和仿真数据。

这也是这个 demo 在不熟悉平台上仍然成立的原因：AVFoundation 的 API 可以查，判断一个 ABR 策略好不好不能查。

## 四、待办事项

当前结论的适用边界已经清楚，以下四项按优先级排列：

**1. 真机验收（阻塞项）。** 所有结论目前只在离线仿真层成立。需要在 Network Link Conditioner（3G profile）下回放真实 HLS 流，对比真机 QoS 与仿真预测的偏差。这是所有参数写回代码的前置条件。

**2. MPC 代价权重搜参结果写回。** 搜出的最优组合在测试集上是 2299 kbps / 9.89s / QoE 0.562，码率涨 4.6 倍而卡顿只降 0.4s —— **收益好得可疑**。我倾向于认为仿真高估了：`preferredPeakBitRate` 在真实 AVPlayer 上有 1~2s 响应延迟，仿真里没建模。在真机确认之前不写回。

**3. QoS 日志落 CSV。** 真机侧把每 0.5s 的 buffer / 码率 / 观测吞吐 / 切档 / 卡顿写入本地文件，用来定量校准仿真器与真实 AVPlayer 的偏差。目前偏差只能定性推测。

**4. 补齐 BBA 搜参结果的真机验证。** `reservoir=6 / cushion=15 / hysteresis=0.95` 这组同样未写回。
